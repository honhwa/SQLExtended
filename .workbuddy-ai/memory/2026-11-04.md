## 修复 VsSDK.targets 导入失败（IDE 报 "was not imported ... due to the file not existing"）

- 现象：SQLExtended.csproj 第 366 行 Import 报错，错误路径为 `G:\nuget\packagesmicrosoft.vssdk.buildtools\...`。
- 根因：用户级 `%APPDATA%\NuGet\NuGet.Config` 的 `globalPackagesFolder` 写成 `G:\nuget\packages`（无尾部分隔符），
  NuGet 原样写进 `obj\*.nuget.g.props` 的 `$(NuGetPackageRoot)`；手写的
  `$(NuGetPackageRoot)microsoft.vssdk.buildtools\...` 直接拼接导致 `packages` 与包名粘连。NuGet 自己生成的
  import 都写成 `$(NuGetPackageRoot)\microsoft...`，所以只有这一行出问题。
- 修复：改为 `<Import Project="$(PkgMicrosoft_VSSDK_BuildTools)\tools\vssdk\Microsoft.VsSDK.targets" />`，
  并给 PackageReference 加 `GeneratePathProperty="true"` 保证该属性被生成；顺带消除了硬编码版本号。
- 注意：本机沙箱禁止执行 MSBuild/dotnet build，只做了 XML 合法性 + 目标文件存在性静态校验，需在 VS 内重新加载项目验证。

## 加密存储过程解密：DAC 被占用后永久失败的问题

- 背景：解密功能（Decryption/）早已实现，原理是 DAC + XOR（唯一可行路径）。用户报错是 DAC 槽被占用。
- 真 bug：`ModuleDecryptionService` 把 DacUnavailableException 一律写入 `UnavailableServers`，**瞬时**的「DAC 忙」
  被当成「这台服务器没有 DAC」永久缓存 → 一次占用就让整个会话的解密全废，只能靠 Clear All Cache 恢复。
- 修复：
  - `DacConnectionFactory.IsBusy(ex)`（只检查 SqlException，绝不看包装异常文本——包装文本里就含 "dedicated administrator
    connection"；同时匹配错误号 17809/17810，因为消息文本会被服务器本地化）＋ `LooksLikeBusyText`。
  - `ModuleDecryptionService.Busy` + `BusyMemo`(5s)：忙只短期记忆；`OpenDac` 重试 2 次（400ms/1200ms）；永久失败仍进
    `UnavailableServers`。
  - `DescribeDacHolder`：最后一次尝试时用普通连接查 sys.dm_exec_sessions，直接把「谁占着 DAC」写进错误信息。
- 测试：新增 `SQLExtended.Tests/Decryption/DacBusyClassificationTests.cs`（含「包装异常文本不得被判为 busy」的回归测试）。
  实测：解密相关 56 个测试全过，解决方案 0 error。
- 文档：`Decryption/CLAUDE.md` 增加「busy 不可与永久失败同样缓存」一节。


## 解密失败第二轮：error 43（DAC 端口无法解析）——已在本机实测定位

- 现象：`-- Could not open a dedicated administrator connection ... (provider: SQL Network Interfaces, error: 43 -
  An error occurred while obtaining the dedicated administrator connection (DAC) port. Make sure that SQL Browser is running)`。
- 本机实测（sqlcmd 直连，非猜测）：
  - 本机只有 Express 实例：`MSSQL15.SQLEXP2019`、`MSSQL12.SQLEXPRESS`（EngineEdition=4）。
  - ERRORLOG 原文：`Dedicated administrator connection support was not started because it is disabled on this
    edition of SQL Server. ... restart SQL Server using the trace flag 7806.` → **Express 默认不启 DAC 监听**，这才是根因。
  - `sys.tcp_endpoints` 中 DAC 端点 port=0；`remote admin connections`=0；`SQLBrowser` 服务未安装；
    实例 `SuperSocketNetLib\Tcp\Enabled=0`（TCP 协议关闭，本机连的是共享内存）。
  - 普通连接即使 sysadmin 也读不到 `sys.sysobjvalues`（Msg 208）→ **无 DAC 就没有第二条解密路线**，已排除。
  - 目标对象确实存在：`MESWD_241023.dbo.wsp_QueryReport`（加密）。
- 代码改动：
  - `DacConnectionFactory.Open`：非 busy / 非登录失败时调用 `ProbeDacEndpoint`（普通连接查 EngineEdition、
    remote admin connections、`sys.tcp_endpoints` 的 DAC 端口、Tcp Enabled、MachineName 判断远端），
    拿到端口就用 `ADMIN:host,port`（`BuildConnectionString(..., dacPort)` + `StripToHost`，去掉实例名）重试一次。
    注意：**DAC 端点的 type_desc 是 'TSQL'**，必须按 `name='Dedicated Admin Connection'` 过滤。
  - 新错误文案按 EngineEdition 分支：Express→7806+重启（TCP 关时附带提示）；远端且 remote admin=0→sp_configure；
    有端口→报出端口与 ADMIN:host,port 尝试结果；否则提示 ERRORLOG。
  - `DacUnavailableException.Permanent`：只有登录被拒 / Azure 才永久缓存；其余进 `Transient`（busy 5s，
    "完全连不上" 2 分钟，`UnreachableMemo`）。`Busy` 字典改名 `Transient`。
  - 新增 `SoluitionDocs/Queries/dac-availability-check.sql`（普通连接可跑，输出事实表 + verdict），已在本机实跑验证。
- 验证：solution 0 error；解密相关 63 个测试全过；用临时测试实跑 `Open()` 确认新文案端到端正确（随后删除该临时测试）。
- 待用户执行：Configuration Manager 给实例加启动参数 `-T7806`（必要时同时启用 TCP/IP）→ 重启实例 → 重新解密。

## 解密第三轮：DAC 已监听但仍 error 43 —— 实测推翻两个假设，已打通并端到端验证

- 用户已加 -T7806 并重启（13:30）。ERRORLOG：`Dedicated admin connection support was established for
  listening remotely on port 11618.` → 监听器确实起来了，但客户端拿不到端口（命名实例 + SQL Browser 未安装）。
- 三个实测结论（都推翻了「显然」的做法）：
  1. `sys.tcp_endpoints.port` **不可用**：DAC 明明监听 11618，该视图仍返回 0（普通 TDS 端点同样返回 0）。
     候选端口只能取 `sys.dm_tcp_listener_states`，且其中 DAC 端点 `type_desc` 也是 'TSQL'，无法按类型区分。
  2. `ADMIN:host,port` **不是合法连接串**：SqlClient 报 provider error 25「Connection string is not valid」。
     可用的是普通 `tcp:host,port` 直接指向 DAC 端口 —— 实测会落到 DAC 端点（endpoint 名 = Dedicated Admin
     Connection，且能读 sys.sysobjvalues）。`ADMIN:` 只是「让客户端去问 SQL Browser 找端口」的写法，不是服务器要求的标志。
  3. 连上 ≠ 是 DAC：实例所有监听端口都接受连接，必须查 `sys.dm_exec_sessions`+`sys.endpoints` 确认落在哪个端点。
- 代码：`Open` → 失败后 `ProbeDacEndpoint` 收集候选端口 → 逐个 `tcp:host,port` 连接 + `IsDacSession` 验证 →
  成功即返回。`BuildConnectionString(...,port)` 改为 `BuildDirectConnectionString`（tcp:host,port，去实例名）。
- 端到端验证：`SoluitionDocs/Queries/decrypt-module-probe.sql` 经 `tcp:localhost,11618` 实跑，
  `dbo.wsp_QueryReport`（56488 字节密文 / 28244 字符）完整解出为 CREATE PROCEDURE。
- 顺手修：
  - `version.txt` 被写入一行 `exec dac-availability-check`（无换行），导致 NuGet 还原报 NU1105
    「not a valid version string」，整个解决方案无法 build。已还原为 `2026.11.4.1230`。
  - `decrypt-module-probe.sql` 的回滚校验拿整个 imageval（varbinary(max)，56KB）比 `SUBSTRING(@origCipher,1,8000)`，
    凡是超过 8KB 的模块都会误报 WARNING；改为单行比全长、多行比首 8KB。
  - `dac-availability-check.sql` 重写：端口从 ERRORLOG 解析（不能用 sys.tcp_endpoints），
    并修掉 `PATINDEX('%port %')` 命中 "support " 导致解析出 0 的 bug；脚本改为纯 ASCII（sqlcmd 按 ANSI 读，破折号会乱码）。
- 结论：**SQL Browser 在这台机器上不需要**（也没安装）。63 个解密测试全过，solution 0 error。
